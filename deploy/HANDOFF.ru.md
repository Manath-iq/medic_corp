# Передача сайта и перенос на сервер заказчика

## Сначала прочитать

Это **демо**, не готовый медицинский production-сервис. Не менять визуальный стиль,
не пересоздавать базу и не запускать seed поверх данных редакторов.
GitHub содержит код и исходные материалы для локального прототипа, но НЕ текущий
контент из CMS. Одного `git clone` недостаточно для переноса действующей админки.

В корне приватный локальный README исключён из Git; публичная инструкция находится
в `.github/README.md`. Подробности CMS — `cms/README.md`, инфраструктуры —
`deploy/README.md`. Перед правками Next читать `cms/AGENTS.md` и документацию
установленной версии Next. Не обновлять версии зависимостей заодно с переносом.

## Текущий демо-сервер

- Сайт: https://clinic.manath.site/ ; CMS: https://clinic.manath.site/admin.
- Hostkey, Ubuntu 24.04, Docker Compose, Caddy + автоматический Let's Encrypt.
- Логин CMS: `admin`; пароль хранится приватно, его нет в Git.
- SSH использует отдельный ключ. На рабочем Mac владельца:

```sh
ssh -i ~/.ssh/medic_corp_hostkey -o IdentitiesOnly=yes root@clinic.manath.site
```

Если DNS ещё не работает, IP берётся из панели Hostkey или локальной приватной
заметки `docs/17-vps-demo.md`. С другого компьютера ключ автоматически не появится:
владелец должен предоставить доступ защищённым способом. Не печатать приватный ключ
или пароли в чате. Старый пароль из письма Hostkey заменён; SSH по паролю отключён.

На сервере:

```sh
cd /opt/medic-demo/app
docker compose --env-file /opt/medic-demo/runtime.env -f deploy/compose.yml ps
docker compose --env-file /opt/medic-demo/runtime.env -f deploy/compose.yml logs --tail 50 cms site web
```

Секреты: `/opt/medic-demo/runtime.env`, начальный пароль CMS:
`/opt/medic-demo/admin.env` (права 600). Не выводить эти файлы в публичные логи.
На Mac пароль доступен владельцу в `~/.local/share/medic-demo/admin.env`.
После изменения пароля в интерфейсе этот файл автоматически не обновится.

## Как устроен запуск

1. Vite собирает браузерную часть в `dist`, SSR — в `dist-server`, с `--base /`
   и `VITE_CMS_URL=same-origin`. Node-сервис `site` рендерит опубликованные данные CMS.
2. Next собирает серверную CMS; запуск через `next start`, НЕ `next dev`.
3. Caddy выдаёт JS/CSS/изображения, HTML направляет в `site`, а `/admin`, `/api`,
   `/_next` — в CMS. Sitemap и robots формируются SSR-сервером.
4. Данные находятся в `/opt/medic-demo/storage`, не внутри Docker-образа.
   SQLite: `data/clinic.db`, медиа: `uploads`, история: `data/document-history`.
5. Внешние порты — 22/80/443. CMS 3001 и SSR 4175 не публикуются. Docker может обходить
   UFW, поэтому запрет в UFW не заменяет отсутствие port mapping у CMS.
6. `restart: unless-stopped` поднимает сервисы после перезагрузки.
7. Caddy перенаправляет старые `/medic_corp/...` ссылки на `/...`, сохраняя query.
8. При `SEO_INDEXABLE=false` robots и X-Robots-Tag запрещают индексацию, но не
   являются защитой от просмотра. Это режим по умолчанию для демо.

GitHub Actions продолжает публиковать отдельный статический вариант на Pages.
GitHub Pages не поддерживает CMS/SSR. Push в GitHub не обновляет VPS автоматически.

## Перед переносом

- Получить разрешение владельца нового сервера, SSH-доступ и окончательный домен.
- Проверить, что на новом сервере нет чужих сервисов/данных и занятых 80/443.
  Ничего не переустанавливать и не чистить автоматически.
- Установить Docker Engine + Compose по официальной инструкции для ОС.
- Создать SSH-ключ/пользователя для нового владельца. Проверить вход в НОВОМ сеансе
  до отключения паролей. Не оставлять единственную копию ключа у разработчика.
- Обеспечить резервную копию исходного сервера; на время финального копирования
  запретить редакторские изменения, чтобы они не потерялись между снимком и DNS.

## Перенести данные, а не только код

На старом сервере:

```sh
systemctl start medic-demo-backup.service
```

Архив появляется в `/opt/medic-demo/backups/`. Он включает `storage` и
`runtime.env`, поэтому содержит секрет! Копировать только через SSH/SCP, хранить
с правами 600, не прикладывать к issue и не добавлять в Git.

На новом сервере разместить код из этого репозитория в `/opt/medic-demo/app`.
Название каталога сохранено в compose и backup-скриптах: оно не означает,
что следует подключаться к старому хостингу. Если менять путь, изменить ВСЕ ссылки.
Архив сначала распаковать в отдельный закрытый каталог, проверить содержимое и
SQLite `PRAGMA integrity_check`. Потом разместить `storage` и `runtime.env` в
`/opt/medic-demo/`. Контейнеры пока не запускать. Установить владельца storage
UID/GID 1000, права корневого каталога storage 700, runtime.env 600.

Не переносить node_modules, .next, dist, локальные .env, test-results или Git-историю
через архив данных. Не заменять рабочую базу локальной устаревшей копией.

## Новый домен и сборка

У DNS-провайдера: A-запись выбранного имени → IPv4 нового сервера.
CNAME одновременно для этого имени не нужен. Удалять чужие записи нельзя.
Проверить отсутствие конфликтующего AAAA и ограничивающего выпуск CAA.

В серверном `runtime.env` установить (значения здесь — пример, не реальные секреты):

```dotenv
PUBLIC_ORIGIN=https://clinic.customer.example
PAYLOAD_SECRET=REPLACE_WITH_A_LONG_RANDOM_SECRET
HTTP_BIND=0.0.0.0:80
HTTPS_BIND=0.0.0.0:443
SEO_INDEXABLE=false
```

PUBLIC_ORIGIN — без завершающего `/`. Смена PAYLOAD_SECRET завершает старые сессии;
новый секрет генерируется на сервере, не записывается в Git. Пароли пользователей
при переносе базы сохраняются. При необходимости явно сменить пароль admin через
`deploy/provision-admin.ts`, передав DEMO_ADMIN_PASSWORD защищённым env-файлом.
Этот скрипт меняет только существующего admin, не создаёт новые учётки.

```sh
cd /opt/medic-demo/app
docker compose --env-file /opt/medic-demo/runtime.env -f deploy/compose.yml build
docker compose --env-file /opt/medic-demo/runtime.env -f deploy/compose.yml up -d --wait
```

Конфигурация CMS зависит от URL при сборке. Одного restart после смены домена
недостаточно: пересобрать и проверить три сервиса. 80/443 должны быть доступны извне: Caddy получит и будет продлевать
сертификат. Не запускать повторные выпуски сертификата в цикле при ошибке DNS.

Первое демо было развёрнуто копией уже заполненной локальной SQLite. Production
schema push отключён. Если базы нет, сначала создать локальный прототип через
`npm run local`, сделать согласованный backup и перенести его. Это режим демо,
а не замена миграций для рабочего сайта. Любые изменения schema.ts требуют
Payload migrations, проверенных на копии актуальной базы до обновления сервера.

## Резервирование

Установить `deploy/medic-demo-backup.service` и `.timer` в `/etc/systemd/system/`,
выполнить daemon-reload, enable --now timer. Ночной backup: 03:15 UTC + до 10 минут,
14 дней хранения. CMS кратко останавливается для согласованности базы и файлов.
В этот промежуток SSR может возвращать 503 — это не непрерывное резервирование.
Обязательно настроить внешнее хранение: локальный диск VPS не защищает от его потери.
В текущем демо есть разовая внешняя копия на Mac, но не регулярное внешнее расписание.

Восстанавливать только при остановленной CMS: сохранить текущее состояние,
распаковать выбранный архив, вернуть владельца 1000:1000, запустить совместимую
версию кода, проверить сайт и файлы. Старый сервер не удалять до полной приёмки.

## Проверка и передача

- DNS у авторитетных серверов и публичных резолверов; HTTPS без игнорирования ошибок.
- HTTP → HTTPS; главная, каталог, врач, цены, новости, документы и фото.
- Вход admin через форму, публикация контрольного изменения и его отмена.
- Preview доступен сотруднику, но не анонимному посетителю.
- Проверить перезапуск контейнеров и сохранение контента/загрузок.
- Сделать backup, распаковать отдельно, проверить целостность и пробный запуск.
- `deploy/verify.mjs`: DEMO_ORIGIN и DEMO_CREDENTIALS_FILE (приватный env-файл
  с DEMO_ADMIN_PASSWORD). Нужен Chromium Playwright. Скрипт временно меняет цену,
  возвращает исходную и пишет отчёт в исключённый из Git `test-results/vps`.
- Прямую доступность проверять из сети заказчика. Тест через SSH-туннель проверяет
  приложение, но не доступность из произвольной сети. При первом запуске прямой
  трафик с Mac обрывался, туннельный тест прошёл; владелец подтвердил работу сайта.
- Передать владельцу доступы, резервные копии, SSH-ключи и инструкцию защищённо;
  удалить лишние доступы разработчиков только после проверки доступа владельца.

Перед официальным запуском отдельно решить юридические материалы, персональные
данные, размещение и карту 301 старых URL; выполнить [SEO-чек-лист](SEO.ru.md).
Серверный HTML реализован; индексация демо намеренно закрыта. Форм пациентов, 1С и
почтового восстановления пароля в этой поставке нет.
